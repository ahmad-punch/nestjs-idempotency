# Design

The central decision is that the store owns both the lock and the record under a single key, and every write is conditional on a per-request lease token: `acquire` creates an in-progress record with `SET NX PX` (or its in-memory equivalent), and `complete` and `release` only act if the stored value still holds the caller's token, which Redis checks atomically in a Lua script. That keeps the whole protocol to three operations that any key-value store with compare-and-set can implement, and it means a request whose lock expired mid-flight can never overwrite the record of the request that took over its key. The trade-off is that the lock has a fixed lifetime (`lockTtlSeconds`) instead of being renewed while the handler runs: a handler slower than the lock can execute twice if the client retries after the lock expires, and its response is then not stored (a warning is logged). We accept that because heartbeating a lock adds timers, failure modes and store round trips to every request to protect against handlers that already exceed most HTTP client timeouts; the fix for a slow handler is a larger `lockTtlSeconds`, and the guarantee for every handler that finishes within it is exact. A second, smaller trade-off is that errors are never stored: a thrown exception frees the key so a transient failure can be retried with the same key, at the cost of not replaying deterministic 4xx errors.
